1. Executive Summary

1. 摘要

Swarm Visibility is not one storage backend or one UI. It is a two-layer observability model for agent systems. Developers need traces, metrics, spans, latency, failure signals, and cost attribution across many runs. Users need a clear replay of what happened in one session and what to do next.

Swarm Visibility 不是单一存储后端或单一界面，而是智能体系统的双层可观测模型。 开发者需要跨多次运行的 trace、metric、span、延迟、失败信号和成本归因； 用户需要看到某个会话中发生了什么，以及下一步应该如何处理。

OTel Layer: Developer Visibility OTel 层：开发者可见性

Instrumented OpenTelemetry spans and future metrics exported to Langfuse, collectors, Prometheus, and Grafana.

通过 OpenTelemetry span 和后续 metric，把数据导出到 Langfuse、Collector、Prometheus 与 Grafana。

TraceHound Layer: User Visibility TraceHound 层：用户可见性

A built-in session and turn viewer that reads existing history files and explains outcomes, errors, tokens, tools, and costs.

内置的会话与回合查看器，读取已有 history 文件，并解释结果、错误、token、工具和成本。

3. Holistic Architecture

3. 整体架构

Agent runtime activity
  │
  ├── Developer layer: OpenTelemetry
  │       Runner.callback_framework / DeepAgentRail / backend bridges
  │       └── spans, traces, metrics, cost attributes
  │           └── OTLP Collector ── Langfuse / Prometheus / Grafana
  │
  ├── User layer: TraceHound
  │       history.jsonl + metadata.json
  │       └── sessions, turns, event timeline, outcome classification
  │           └── JiuwenSwarm web UI + LLM analysis
  │
  └── Shared semantics
          session_id, request_id, agent_id, model, tool, token usage,
          cost version, error category, trajectory step

The systems stay separate by design. OTel is push-based and operational. TraceHound is file-based and user-facing. They combine through vocabulary, IDs, cost semantics, and error classification rather than by sharing one runtime path.

两个系统应保持分离。OTel 是推送式、偏运维的链路；TraceHound 是基于文件、 面向用户的链路。它们通过术语、ID、成本语义和错误分类连接，而不是强行合并为同一条运行时路径。

Independent operation: TraceHound can work without any OTel enhancement being enabled or installed. It reads the agent trajectory/history records that JiuwenSwarm already writes, so users still get session replay, turn analysis, outcome classification, and LLM analysis even when no spans, collector, Langfuse, Prometheus, or metrics pipeline exists.

独立运行：TraceHound 不依赖任何 OTel 增强是否启用或安装。 它读取 JiuwenSwarm 已经写入的智能体 trajectory/history 记录。因此即使没有 span、 Collector、Langfuse、Prometheus 或 metrics pipeline，用户仍然可以使用会话回放、 回合分析、结果分类和 LLM 分析。

7. Non-Goals

7. 非目标

  • Do not merge agent_teams/observability and extensions/tracer_otel providers.
  • Do not re-instrument TraceHound; it must preserve zero additional hot-path overhead.
  • Do not force OTel and TraceHound into one database or one UI.
  • Do not emit cost as exact when model pricing is unknown or stale.
  • 不要合并 agent_teams/observability 与 extensions/tracer_otel 的 provider。
  • 不要为了 TraceHound 重新增加 instrumentation；它必须保持热路径零额外开销。
  • 不要强行把 OTel 和 TraceHound 合并到同一个数据库或同一个 UI。
  • 当模型价格未知或过期时，不要把成本展示为精确值。
