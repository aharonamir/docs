1. Current Repository Status

The repository already has substantial tracing support. This page reflects the code as of 2026-08-09 and supersedes the older roadmap language that assumed only two observability systems existed.

Team-Agent OTel — agent_teams/observability/

Team observability is wired through the global Runner.callback_framework. It emits team roots, per-iteration agent spans, single-round subagent invoke spans, LLM spans, tool spans, and task/member/message spans from the team monitor stream.

team.{name} root span, finalized by Runner ├── agent.{member}.task_iteration.N ObservabilityRail │ ├── llm.call OtelCallbackHandler │ │ └── llm.reasoning conditional child span │ └── tool.{name} OtelCallbackHandler ├── agent.{member}.invoke single-round subagent span ├── task.{task_id} OtelTeamMonitorHandler │ ├── task.created / claimed / completed │ └── msg.{from}->{to} └── member.{name}.spawned OtelTeamMonitorHandler

Key design: ActiveSpanTracker keeps strong references to open spans and cleanup paths drain orphaned child spans during cancellation and finalization. Future work should extend this model rather than adding a second ad hoc span lifecycle.

Standalone BaseAgent/Workflow Extension — extensions/tracer_otel/

The extension traces standalone BaseAgent and workflow single-invocation paths through core.session.tracer. It owns an independent TracerProvider and deliberately does not call trace.set_tracer_provider().

FileResponsibility
config.pyOtelTracerConfig — frozen dataclass, independent from ObservabilityConfig
setup.pyinit_otel_tracer(config) — creates own TracerProvider, deliberately does NOT call set_tracer_provider() to avoid conflict with System A
handler.pyOtelAgentHandler, OtelWorkflowHandler — full span lifecycle via TraceExtAgentHandler / TraceExtWorkflowHandler
otel_rail.pyOtelRail(AgentRail) — opt-in single-invoke hooks via session tracer
span_manager.pyOtelAgentSpanManager, OtelWorkflowSpanManager

Important: this extension does not cover standalone DeepAgent task-loop iterations. That gap belongs in agent_teams/observability/ObservabilityRail or a shared successor rail, because task-loop spans need DeepAgentRail hooks.

Backend Runtime Bridges — claude/ and codex/

The repo now includes backend-specific bridges. Claude stream chunks can produce turn, tool, and reasoning spans. Codex support can read rollout traces, receive filtered native logical model-call spans over loopback OTLP/HTTP, and correlate model/tool records into Jiuwen spans.

AreaStatus

codex/otel_receiver.pyPresent; filters Codex native spans to logical model-call spans.
codex/bridge.pyPresent; correlates model/tool records and emits spans.

Phase 0: Audit Tests And Freeze The Current Contract

Add or update tests that lock down the current team trace tree, subagent invoke nesting, cancellation cleanup, Claude/Codex bridge behavior, and shutdown idempotency. This protects the existing span lifecycle before standalone support changes parent resolution.

Phase 2: Session-Level Spans

SessionEvents.AGENT_SESSION_CREATED is available and is triggered by AgentSession.pre_run() and the session controller. There is no SESSION_CLOSED or AGENT_SESSION_CLOSED event, so this phase must first decide where spans close.

session.{session_id} root if lifecycle owner can close it ├── team.{name} or agent.{name} child root for one run │ └── agent.{member}.task_iteration.N └── close-time metadata: duration, agent_count, optional totals

Likely new file: session_span.py with SessionSpanManager

  • open_session_span(session_id, tracer) — creates the root and stores ownership state
  • close_session_span(session_id) — ends the span from an explicit lifecycle path
  • get_session_span(session_id) — returns open span or None

Risk: do not leave long-lived session spans open until process shutdown unless that is the intended lifecycle. Add a close event only at a real lifecycle owner.

Phase 3: Ordered Trajectory Events

Each agent iteration span has child LLM/tool spans, but not a compact ordered list of what happened. Add trajectory.step events before the iteration span closes.

agent.{member}.task_iteration.N events: trajectory.step {seq: 1, kind: "llm", model: "...", prompt_tokens: 1240} trajectory.step {seq: 2, kind: "tool", name: "bash", duration_ms: 1100} trajectory.step {seq: 3, kind: "llm", model: "...", completion_tokens: 120}

Start with span events instead of a durable store. Reuse agent_evolving.trajectory types only if they fit cleanly; do not couple the tracing hot path to training/evolution persistence.

Phase 4: Metrics Infrastructure

Add a disabled-by-default MeterProvider and recorder API. Metrics should remain opt-in so trace-only users do not get new exporter side effects.

Token Usage Counter

Prompt/completion/total tokens by model and agent_id. Cumulative counter.

LLM Latency Histogram

Duration (ms) per LLM call by model. Enables p50/p95/p99 reporting.

Tool Call Counter + Histogram

Call count and duration per tool_name. Error rate as separate counter.

Task Iteration Histogram

Duration per task iteration by agent_id. Basis for task SLOs.

Config additions: metrics_enabled: bool = False, metrics_endpoint: str = "", and a metrics exporter selector.

Phase 5: Cost And Aggregation

Add useful summaries while being explicit that cost is estimated. Pricing should be overrideable and unknown models should produce token totals without pretending a USD estimate is known.

task.{task_id} attributes added by Phase 5: agentteam.task.total_prompt_tokens: 4820 agentteam.task.total_completion_tokens: 1340 agentteam.task.total_tool_calls: 8 agentteam.task.estimated_cost_usd: 0.0182 agentteam.task.cost_pricing_version: "..." agentteam.task.member_contributions: {"alice": {...}, "bob": {...}}

5. Architecture Overview

Coexisting Tracing Paths

agent_teams/observability/ extensions/tracer_otel/ backend bridges ─────────────────────────────── ───────────────────────── ───────────────────────── Runner.callback_framework core.session.tracer Claude/Codex runtime data Global provider private provider uses team observability runtime Team + future DeepAgent BaseAgent/workflow backend-specific span enrichment

Target Parent Resolution

For team observability LLM/tool spans: 1. current agent span, when recording 2. current team span, when recording 3. future standalone root/current span, for explicit standalone DeepAgent opt-in 4. future session span, only if lifecycle-safe close behavior exists

Data Flow

Agent Code │ ├─ Runner.callback_framework ──→ OtelCallbackHandler ──→ LLM span │ ──→ OtelCallbackHandler ──→ Tool span │ ──→ TrajectoryTracker.record_*() (Phase 3) │ ──→ MetricsRecorder.record_*() (Phase 4) │ ──→ CostTracker.record_usage() (Phase 5) │ ├─ TeamEvent stream ──→ OtelTeamMonitorHandler ──→ Task / Member spans │ ──→ TaskAggregator (Phase 5) │ ├─ DeepAgentRail ──→ ObservabilityRail ──→ Agent iteration span │ ──→ TrajectoryTracker.emit_to_span() (Phase 3) │ ──→ MetricsRecorder.record_iteration() (Phase 4) │ └─ SessionEvents ──→ SessionSpanManager (Phase 2) All spans export via OTLP to: OTel Collector (deploy/observability/) ──→ Langfuse (traces) ──→ Prometheus (metrics, Phase 4)

6. What We Can Add Now

The highest-value additions are standalone DeepAgent tracing, disabled-by-default metrics, ordered trajectory events, and cost estimates with explicit uncertainty. Session root spans are useful but should wait for a clear close lifecycle.

AdditionWhy It Fits Current State
Standalone DeepAgent tracingCloses the largest gap while reusing existing callback and rail machinery.
MetricsAdds dashboards and alerting without changing trace behavior when disabled.
Trajectory eventsSmall addition that makes iteration spans much easier to inspect.
Cost estimatesUses existing usage attributes if pricing is versioned and overrideable.
Session rootsValuable, but only after the close/finalization contract is settled.
