1. Overview

openjiuwen.agent_teams is a framework for orchestrating multi-agent teams where a leader agent coordinates one or more teammate agents (and optionally human-agent avatars) to collaboratively solve complex tasks. Teams communicate through a database-backed task board, point-to-point messaging, and a pub/sub event bus.

The design separates specification (JSON-serializable blueprints) from runtime (live agent processes, event loops, messager transports), enabling both in-process and cross-process deployment.

2. Core Concepts

2.1 Roles

LEADER Leader

Owns the team. Creates tasks, spawns/shuts down teammates, approves plans and tool calls, broadcasts instructions. Runs the coordination kernel that subscribes to all team events.

TEAMMATE Teammate

An autonomous agent spawned by the leader. Claims tasks, executes work, sends messages. Waits for first-iteration gate before polling its mailbox. Can run in-process or as a subprocess.

HUMAN_AGENT Human-Agent

A first-class member representing an external human collaborator. Has a DeepAgent runtime driven by HumanAgentInbox. Limited tool set (view_task, member_complete_task). Enabled via HITT (Human-in-the-Team).

2.2 Team Lifecycle

ModeDescription
TEMPORARYTeam is created, runs one round, then shuts down and cleans up. Default.
PERSISTENTTeam pauses between rounds instead of shutting down. Can be resumed via activate() with RESUME_FROM_PAUSE.

2.3 Team Modes

ModeDescription
defaultLeader spawns teammates dynamically via spawn_member tool.
predefinedAll teammates declared upfront in predefined_members; no dynamic spawn.
hybridPredefined members exist, but the leader can still spawn additional teammates at runtime.

2.4 Teammate Execution Modes

ModeDescription
build_modeTeammates execute tasks immediately. Leader does not approve plans or tool calls. Default.
plan_modeTeammates submit plans for leader approval before executing. Tool calls can be intercepted for leader sign-off.

3.1 Dispatch Decision Table

The runtime manager resolves each activate() call into a RunAction based on the state of three signals:

  • team_in_db — does the static team table have a row?
  • team_in_session — does the session checkpoint have a bucket?
  • pool_entry — is there a live runtime in the pool?

4. Specifications (Specs)

All configuration is expressed as Pydantic BaseModel instances that round-trip through JSON. This makes specs transportable across process boundaries and persistable in session checkpoints.

4.1 Spec Hierarchy

  TeamAgentSpec                         Top-level: composes everything
  ├── agents: dict[str, DeepAgentSpec]  Per-role agent specs ("leader", "teammate")
  ├── leader: LeaderSpec                Leader identity (name, persona, model_name)
  ├── predefined_members: list[TeamMemberSpec]  Pre-declared teammates
  ├── model_pool: list[ModelPoolEntry]  Shared LLM endpoint pool
  ├── model_router: ModelRouterConfig   Single-endpoint router (alternative to pool)
  ├── model_pool_strategy               "round_robin" | "by_model_name" | "router"
  ├── transport: TransportSpec          Messager backend ("inprocess" | "pyzmq")
  ├── storage: StorageSpec              Database backend ("sqlite" | "postgresql" | "memory" | ...)
  ├── worktree: WorktreeConfig          Git worktree isolation
  ├── workspace: TeamWorkspaceConfig    Shared workspace config
  ├── memory: TeamMemoryConfig          Per-member memory isolation
  ├── spawn_mode                        "inprocess" | "process"
  ├── teammate_mode                     "build_mode" | "plan_mode"
  ├── team_mode                         "default" | "predefined" | "hybrid"
  ├── lifecycle                         "temporary" | "persistent"
  ├── enable_hitt: bool                 Human-in-the-Team capability ceiling
  ├── language: str                     Prompt locale ("cn" | "en")
  └── agent_customizer: Callable        In-process hook for platform adapters

  DeepAgentSpec                         Per-role agent definition
  ├── model: TeamModelConfig            LLM model (client + request config)
  ├── card: AgentCard                   Identity metadata
  ├── system_prompt: str                System prompt
  ├── tools: list[ToolCard | BuiltinToolSpec]
  ├── rails: list[RailSpec]             Behavioral rails
  ├── subagents: list[SubAgentSpec]     Nested sub-agents
  ├── workspace: WorkspaceSpec          Workspace root + language
  ├── sys_operation: SysOperationSpec   Filesystem / sandbox config
  ├── progressive_tool: ProgressiveToolSpec
  ├── approval_required_tools           Tools needing leader approval
  └── ... (vision, audio, skills, etc.)

  TeamSpec                              Runtime team definition (built from TeamAgentSpec)
  ├── team_name, display_name
  ├── leader_member_name
  ├── model_pool + model_pool_strategy
  └── language, metadata

  TeamRuntimeContext                    Per-member runtime context
  ├── role: TeamRole
  ├── member_name, persona
  ├── team_spec: TeamSpec
  ├── messager_config, db_config
  └── member_model: TeamModelConfig     Allocator-assigned model

4.2 Build Pipeline

Calling TeamAgentSpec.build() performs:

  1. Validate reserved names and HITT consistency
  2. Resolve language defaults
  3. Expand model_router into flat model_pool (if set)
  4. Build TeamSpec, messager config, and DB config
  5. Allocate leader model from pool
  6. Construct TeamAgent and call configure(spec, context)

Source: openjiuwen/agent_teams/schema/blueprint.py:332-413

6. Coordination Kernel & Event Bus

The CoordinationKernel owns the internal EventBus and EventDispatcher. It manages the coordination lifecycle:

  start()                         pause() / stop()
  ─────────────────────────────   ─────────────────────────────
  1. Initialize DB                1. Drain agent task
  2. Bind session                 2. Persist allocator state
  3. Recover team (if needed)     3. Mark teammates PAUSED (leader only)
  4. Init workspace               4. Publish STANDBY event (pause only)
  5. Init memory toolkit          5. Unsubscribe transport
  6. Set status → READY           6. Stop event bus
  7. Start event bus              7. Close stream
  8. Subscribe messager           8. Release session

6.1 Inner Events

The event bus processes two internal event types:

  • USER_INPUT — external input enqueued by invoke() / stream()
  • POLL_MAILBOX — triggers the dispatcher to check for pending messages (teammates only, after first iteration)

6.2 Dispatcher

The EventDispatcher is bound as the event bus wake callback. When the bus wakes (new event arrives), the dispatcher:

  1. Processes all pending inner events
  2. Processes all pending external events (from messager)
  3. Handles member lifecycle, message delivery, task board updates, tool approvals

Source: openjiuwen/agent_teams/agent/coordination/

7. Messager Transport

The messager provides two communication primitives:

  • Pub/Sub — topic-based fan-out (team events, broadcasts)
  • Point-to-Point — direct message delivery to a specific agent

7.1 Backends

InProcessMessager

Process-global _Bus singleton with handler-based routing. No serialization. Used when spawn_mode="inprocess".

PyZmqMessager

ZeroMQ-based transport for cross-process communication. Used when spawn_mode="process". Requires pyzmq extra.

7.2 Topic Routing

Topics follow the pattern:

session:{session_id}:team:{team_name}:{topic}

Three topic categories exist: TEAM, TASK, MESSAGE. Each member subscribes to all three; self-published events are filtered by sender_id.

Source: openjiuwen/agent_teams/messager/

8.2 Task Board

Tasks follow a status machine:

  PENDING ──▶ CLAIMED ──▶ PLAN_APPROVED ──▶ COMPLETED
    │            │
    │            └──▶ (reset to PENDING on cancel)
    │
    └──▶ CANCELLED

  Dependencies: depends_on / depended_by edges control claimability.
  A task is claimable only when all its depends_on tasks are COMPLETED.

8.3 Messaging

send_message supports three modes:

  • Point-to-point: to="member_name"
  • Broadcast: to="*"
  • Multicast: to=["m1", "m2"]

Messages are persisted in the database and delivered via the messager event bus. When the leader sends a message, unstarted teammates are auto-started.

Source: openjiuwen/agent_teams/tools/team_tools.py

9. Runtime Manager & Dispatch

TeamRuntimeManager is the process-level owner of the TeamRuntimePool. It provides the public API for the SDK / CLI:

MethodDescription
activate(spec, session)Dispatch + materialize a team (create / recover / resume)
interact(payload)Route an interact payload to the active team (god-view / operator / human-agent)
pause(team_name, session_id)Pause the active runtime
stop_team(team_name, session_id)Tear down the active runtime
delete_team(team_name, session_ids)Delete all persisted state + filesystem
list_active_teams()Read-only snapshots of all pooled teams
get_monitor(team_name, session_id)TeamMonitor for status observation

9.1 Interaction Gate

Each ActiveTeam owns an InteractGate that enforces the run/interact concurrency contract:

  • While a run is in flight, interact() payloads are admitted through the gate
  • When the run is about to exit, the gate closes and waits for in-flight payloads to drain
  • State machine: OPEN → CLOSING → DRAINED

Source: openjiuwen/agent_teams/runtime/manager.py, openjiuwen/agent_teams/runtime/gate.py

10. Spawn Modes

10.1 In-Process Spawn

When spawn_mode="inprocess", teammates run as asyncio.Tasks in the leader's event loop. The InProcessSpawnHandle wraps the task and provides a reference to the teammate's TeamAgent for direct access.

  Leader Event Loop
  ┌────────────────────────────────────────────┐
  │                                            │
  │  ┌──────────┐  ┌──────────┐  ┌──────────┐ │
  │  │ Leader   │  │ Teammate │  │ Teammate │ │
  │  │ DeepAgent│  │ #1 Task  │  │ #2 Task  │ │
  │  └──────────┘  └──────────┘  └──────────┘ │
  │                                            │
  │  InProcessMessager (shared _Bus singleton) │
  └────────────────────────────────────────────┘

10.2 Process Spawn

When spawn_mode="process", teammates run in separate OS processes. Communication goes through PyZmqMessager. The leader serializes the TeamAgentSpec + TeamRuntimeContext into a spawn payload that the child process deserializes via TeamAgent.from_spawn_payload().

Source: openjiuwen/agent_teams/spawn/

11. External Interaction

The framework exposes two parallel input channels for external callers:

UserInbox

Delivers input to the leader's DeepAgent by default. Supports @member_name routing to bypass the leader and post directly to a specific teammate. Also supports broadcast.

HumanAgentInbox

Dispatches input as a send_message from the human-agent avatar. Only available when HITT is enabled. Supports @target routing and team-side callbacks.

11.1 Interact Payload Types

TypeRoutingDescription
GodViewMessageLeader DeepAgentTalk straight to the leader's LLM
OperatorMessageTarget member or broadcastSDK-level operator control
HumanAgentMessageFrom human-agent to targetUser voice through avatar

11.2 String Parsing

Free-form string inputs are parsed by parse_interact_str:

  • # body → GodViewMessage
  • $<name> body → HumanAgentMessage
  • @member body → targeted delivery
  • No prefix → GodViewMessage

Source: openjiuwen/agent_teams/interaction/

12. TeamHarness & DeepAgent

TeamHarness is the sole adapter between TeamAgent and the underlying DeepAgent runtime. All construction, rail mounting, and runtime calls flow through it.

12.1 Rail Mount Order

  1. TeamToolRail — injects team tools into the agent's ability set
  2. TeamPolicyRail — enforces team-level behavioral policies
  3. FirstIterationGate — blocks mailbox polling until first iteration completes (teammates)
  4. TeamWorkspaceRail — workspace lock management and version control
  5. TeamToolApprovalRail — intercepts tool calls for leader approval (plan_mode)

12.2 DeepAgentSpec.build()

Each role's DeepAgentSpec materializes into a live DeepAgent with its own model, tools, rails, subagents, workspace, and sys_operation. The harness wraps this and exposes only the operations that TeamAgent needs:

  • steer(), follow_up() — mid-execution input
  • abort() — cooperative cancellation
  • run_streaming() — chunk-by-chunk output iterator
  • register_rail() / unregister_rail() — dynamic rail management

Source: openjiuwen/agent_teams/harness.py

15. End-to-End Data Flow

15.1 Team Creation

  Caller                  TeamRuntimeManager            TeamAgent (Leader)           DeepAgent
  ──────                  ──────────────────            ──────────────────           ─────────
  activate(spec)
      │
      ├──▶ _build_session()
      ├──▶ _inspect_session()
      ├──▶ decide_run_action() ──▶ CREATE
      ├──▶ spec.build()  ──────────────────────▶  TeamAgent()

      │                                            ├── _setup_infra()

      │                                            │     ├── create TeamBackend

      │     ├── on_created(member_name)

15.3 Messaging Flow

  Leader DeepAgent                Messager Bus              Teammate DeepAgent
  ────────────────                ─────────────              ──────────────────
  send_message(to="dev-1",
               content="Fix bug")
      │
      ├──▶ TeamMessageManager.send_message()
      │       ├── db.message.create()
      │       └── messager.publish(MessageEvent)
      │
      └──▶ "Message sent"            │
                                       │ EventMessage
                                       ▼
                                  InProcessBus / ZMQ
                                       │
                                       │ (filtered: not self)
                                       ▼
                                  EventBus.enqueue()
                                       │
                                       ▼
                                  EventDispatcher.dispatch()
                                       │
                                       ├──▶ mailbox.append()
                                       └──▶ wake agent if idle

                                                             (agent polls mailbox)
                                                             send_message(to="team_leader",
                                                                          content="Done!")
Key design principle: All state is persisted in the database. Events are ephemeral notifications that wake agents to check their mailbox. This means a teammate can recover from a crash and resume by reading its pending messages from the database.
