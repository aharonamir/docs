Auto Harness Architecture

Self-optimizing coding agent framework — openjiuwen/auto_harness/

Overview

Auto Harness is a self-driving coding agent that autonomously improves a codebase. It runs a session that assesses the repository, plans tasks, implements code changes, verifies them with CI, commits, and optionally publishes a pull request — all without human intervention.

The system has two built-in pipeline modes:

Meta Evolve Pipeline

session-scoped

Directly modifies the repository source code. The classic assess → plan → implement → verify → commit → PR → learnings loop. Used for code quality improvements, bug fixes, and feature additions.

Extended Evolve Pipeline

session-scoped

Generates runtime extensions (tools, skills, rails) that extend the agent's own capabilities. Analyzes capability gaps, designs extension packages, implements them in isolated worktrees, verifies with acceptance tests, and hot-loads them into the live agent.

Session Lifecycle

1. Configuration & Bootstrap

Everything starts with AutoHarnessConfig (schema.py:481) — a dataclass that holds all runtime settings:

Paths

  • data_dir — root for all artifacts
  • local_repo — path to local agent-core repo
  • Derived: experience_dir, worktrees_dir, runs_dir, cache_repo_dir, runtime_extensions_dir

Budget

  • session_budget_secs — wall-clock limit
  • cost_limit_usd — cost cap
  • task_timeout_secs — per-task timeout
  • max_tasks_per_session — task cap

Git & CI

  • git_remote, git_base_branch
  • fork_owner, upstream_owner
  • ci_gate_config — CI gate rules YAML
  • fix_phase1_max_retries, fix_phase2_max_retries

Security

  • immutable_files — files the agent must never modify
  • high_impact_prefixes — paths requiring extra caution
  • agent_iterations — per-stage LLM iteration caps

Config can be loaded from YAML via load_auto_harness_config() or constructed programmatically. If the config file doesn't exist, a template is auto-generated.

2. Orchestrator Initialization

AutoHarnessOrchestrator (orchestrator.py:103) is the session controller. On construction it creates:

ComponentRole
ArtifactStoreKey-value store for stage outputs (scoped by task_id)
StageRegistryAll registered stage specs (built-in + extensions)
PipelineRegistryAll registered pipeline specs
ExperienceStoreJSONL-backed archive of past experiences
SessionBudgetControllerWall-clock and cost budget tracker
FixLoopControllerTwo-phase CI fix loop engine
WorktreeManagerGit worktree creation/cleanup for task isolation
GitOperationsGit commands (status, diff, commit, push, PR)
CIGateRunnerRuns CI checks defined in ci_gate.yaml

3. Pipeline Selection

Before any stage runs, the orchestrator calls choose_session_pipeline() (infra/pipeline_selector.py:62) which decides between the two pipelines based on:

  1. Explicit preference — if config.pipeline_preference is set to a specific pipeline name
  2. Signal detection — if task topics contain keywords like "competitor", "absorb", "extend capability", it routes to the Extended Evolve pipeline
  3. Default — falls back to Meta Evolve pipeline

4. Session Execution

run_session_stream() (orchestrator.py:264) is the main entry point. It:

  1. Resets state, starts budget timer
  2. Selects the pipeline
  3. Streams the pipeline's stream(ctx) method
  4. Yields OutputSchema chunks to the caller (CLI, UI, etc.)
  5. Emits a harness_session_finished event when done

Meta Evolve Pipeline

The Meta Evolve Pipeline (meta_evolve_pipeline.py:43) is the classic assess-and-improve loop. Its stage order is:

ASSESS → PLAN → IMPLEMENT → VERIFY → COMMIT → PUBLISH PR → LEARNINGS

Stage: Assess

MetaAssessStage (stages/assess.py:160) evaluates the current repository state:

  • Creates a readonly git worktree snapshot
  • Launches a create_assess_agent() DeepAgent with research tools (web search, fetch)
  • Agent inspects code, runs lint/type-check, checks recent git history, reads past experiences
  • Produces an AssessmentArtifact with a structured report
  • Falls back to a pure-Python assessment if the agent fails

Stage: Plan

MetaPlanStage (stages/plan.py:76) generates optimization tasks:

  • Consumes the assessment report
  • Launches a create_plan_agent() DeepAgent
  • Agent analyzes the report and produces a task list
  • Parses the output into OptimizationTask objects (capped at 1 task per session)
  • Falls back to using input tasks if agent produces nothing

Stage: Implement

MetaImplementStage (stages/implement.py:317) executes code changes:

  • Creates an isolated git worktree for the task
  • Launches the main create_auto_harness_agent() DeepAgent with full tools, rails, and subagents
  • Agent directly edits files, runs commands, uses explore/browser subagents
  • After completion, checks git status/diff to detect what was actually changed
  • Produces a CodeChangeArtifact listing edited files

Stage: Verify

MetaVerifyStage (stages/verify.py:300) runs CI and the fix loop:

  1. Runs all CI gates via CIGateRunner
  2. If CI fails, starts a two-phase fix loop:
    • Phase 1: Agent reads CI errors and fixes code; re-runs CI (up to 10 retries)
    • Phase 2: Evaluator agent reviews quality; if rejected, agent continues fixing (up to 9 retries)
  3. If fix loop exhausts retries, changes are reverted (git discard)
  4. Produces a VerifyReportArtifact

Stage: Commit

CommitStage (stages/commit.py:276) creates a git commit:

  • Collects CommitFacts — branch, dirty files, edited files, allowed files, diff stat
  • Uses EditSafetyRail to track which files the agent actually modified
  • Derives an allowed file list (task-declared files + derived test files, excluding pre-existing dirty files)
  • Launches a commit agent that runs git add + git commit
  • Retries once if the first attempt fails

Stage: Publish PR

PublishPRStage (stages/publish_pr.py:160) pushes and creates a PR:

  • If git_remote and fork_owner are configured, generates a PR draft via LLM
  • Pushes the branch to the remote
  • Creates a PR via GitCode API
  • Records a success experience
  • Produces a CycleResult with PR URL and completion summary

Stage: Learnings

LearningsStage (stages/learnings.py:42) reflects on the session:

  • Launches a create_learnings_agent() that reviews all session results
  • Extracts structured learnings (insights, failures, optimizations)
  • Persists them to the ExperienceStore for future sessions

Extended Evolve Pipeline

The Extended Evolve Pipeline (extended_evolve_pipeline.py:45) generates new runtime extensions (tools, skills, rails) to expand the agent's own capabilities. Its stage order is:

ASSESS EXT → PLAN EXT → BUILD + VERIFY → MERGE → ACTIVATE

Stage: Assess Ext (Gap Analysis)

ExtendAssessStage (stages/assess.py:578) analyzes capability gaps:

  • Launches the assess agent with a gap-analysis prompt
  • Agent produces a markdown table of gaps (feature, current state, impact, feasibility)
  • Output is parsed into Gap objects, sorted by priority (impact × feasibility)
  • Falls back to heuristic gap generation from input tasks

Stage: Plan Ext (Extension Design)

ExtendPlanStage (stages/plan.py:152) designs runtime extensions:

  • Launches a create_design_ext_agent()
  • For each gap, designs an ExtensionDesign with:
    • kind — "capability" or "constraint"
    • components — which components to build (tool, skill, rail)
    • file_plan — directory structure and manifest path
    • depends_on — dependencies on other extensions
  • Constraints are prioritized over capabilities

Stage: Build + Verify (Dependency Waves)

Extensions are built and verified in dependency waves with bounded concurrency:

  1. Implement Ext (ExtendImplementStage): For each design, creates an isolated worktree and launches the task agent to generate the extension package (Python files, harness_config.yaml, skill markdown)
  2. Verify Ext (ExtendVerifyStage): Three-layer verification:
    • Structure check: manifest exists, classes can be instantiated, skill dirs have SKILL.md
    • Lint check: ruff format + ruff check
    • Acceptance tests: Agent generates pytest tests, runs them, and fixes the extension if tests fail (up to 3 attempts)
  3. Promote: Verified extensions are copied to the session runtime directory

Extensions with unmet dependencies are skipped. Extensions with satisfied dependencies run in parallel (up to extension_verify_concurrency).

Stage: Merge

MergeActivationBlock (stages/merge.py:48) combines multiple verified extensions into a single merged package:

  • Calls merge_runtime_extensions() (infra/runtime_extension_merger.py) to deterministically combine all verified extension directories
  • Detects file-path conflicts and generates rename maps for imports and skill references
  • Runs static checks (infra/runtime_extension_static_checks.py) against the merged package: ruff format, ruff check --fix, and structure validation
  • If static checks fail, launches a create_merge_ext_agent() to repair issues (up to 3 rounds)
  • Cleans up source extension directories after successful merge
  • Yields a MergeSuccessResult containing the merged RuntimeExtensionArtifact

Merge is only triggered when multiple extensions were built in the same session. Single-extension sessions skip merge and go straight to activate.

Stage: Activate

ExtendActivateStage (stages/activate.py:45) hot-loads extensions:

  1. Emits an extension_ready event with extension metadata
  2. Creates an __interaction__ event asking the user to accept or reject
  3. If accepted, calls agent.enqueue_harness_config() to hot-load the extension
  4. Streams a testing guide generated by a lightweight agent

Core Subsystems

Execution Contexts

Two context objects flow through the pipeline:

ContextScopeContents
SessionContext Entire session Reference to orchestrator; access to artifacts, messages
TaskContext Single task Extends SessionContext + OptimizationTask + TaskRuntime (agent, worktree path, edit safety rail, etc.)

Artifact Store

ArtifactStore (artifacts/store.py) is a key-value store scoped by task_id. Stages produce artifacts that downstream stages consume. For example:

AssessStage  produces  "assessment"     →  PlanStage     consumes "assessment"
PlanStage    produces  "task_plan"      →  ImplementStage consumes "task_plan"
Implement    produces  "code_change"    →  VerifyStage   consumes "code_change"
Verify       produces  "verify_report"  →  CommitStage   consumes "verify_report"

Experience Store

ExperienceStore (experience/experience_store.py:24) is a JSONL-backed archive:

  • Record: Appends Experience entries (optimization, failure, insight) with dedup within 24h
  • Search: Keyword search with recency-weighted scoring
  • List recent: Returns N most recent experiences

ActiveContextSynthesizer (experience/synthesizer.py:38) condenses experiences into a markdown summary grouped by type (optimizations, failures, insights) with time-decay weighting, suitable for injection into agent prompts.

Key Design Patterns

1. Pipeline & Stage Pattern

Pipelines are composable sequences of stages. Each stage declares consumes and produces artifacts, creating a typed data-flow contract. The PipelineStageMap binds abstract slots (like "assess", "plan") to concrete stage classes, allowing different pipelines to reuse the same slots with different implementations.

2. Worktree Isolation

Each task runs in an isolated git worktree. This ensures:

  • Assess runs on a clean readonly snapshot
  • Implement runs in a writable worktree that can be discarded on failure
  • Extension builds are isolated from each other
  • Multiple extensions can build in parallel without conflicts

3. Two-Phase Fix Loop

The verify stage uses a two-phase approach:

  • Phase 1 (Direct Fix): CI fails → agent reads errors → agent fixes code → re-run CI. Up to 10 retries.
  • Phase 2 (Evaluated Fix): After CI passes, an evaluator agent reviews quality. If rejected, agent continues fixing. Up to 9 retries.
  • If all retries are exhausted, changes are reverted automatically.

4. Experience Accumulation

Every session records experiences (successes, failures, insights) to a persistent JSONL store. Future sessions query this store to:

  • Avoid repeating failed approaches
  • Build on past successes
  • Provide context to the assess and plan agents

The ActiveContextSynthesizer condenses recent experiences into a token-budgeted markdown summary injected into agent prompts via AutoHarnessExperienceRail.

5. Streaming Architecture

The entire pipeline is async-streaming. Every stage's stream() method is an async generator that yields OutputSchema chunks. This allows:

  • Real-time progress reporting to the UI
  • Streaming LLM output without buffering
  • Interaction events (e.g., activate confirmation) embedded in the stream

6. Extension Merge & Conflict Resolution

When multiple extensions are built in a single session, the merge stage (MergeActivationBlock) combines them into one deterministic package:

  • File-path conflict detection — duplicate paths trigger rename with import rewriting
  • Skill reference remapping — skill directories are re-rooted under the merged namespace
  • Post-merge static checks — ruff format, ruff check --fix, structure validation
  • Agent-assisted repair — if static checks fail, a merge agent fixes issues (up to 3 rounds)

Single-extension sessions skip merge entirely and activate the verified extension directly.

7. Runtime Extension Hot-Loading

The Extended Evolve pipeline generates extensions that can be hot-loaded into a running DeepAgent without restart:

  1. Extension is built and verified in an isolated worktree
  2. Verified extension is promoted to the session runtime directory
  3. User confirms activation via an interaction event
  4. agent.enqueue_harness_config() queues the extension for loading
  5. Extension takes effect on the next query to the agent
