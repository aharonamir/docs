1. Overview

openjiuwen/agent_evolving/ is the self-evolving optimization framework for AI agents. It enables agents to automatically improve their performance through iterative cycles of evaluation, signal detection, parameter optimization, and writeback.

The package supports two complementary evolution paradigms:

Offline Batch Evolution

Run the agent against a dataset of cases, evaluate the outputs, extract trajectories, detect failure signals, and optimize prompts / tool descriptions / skills in a supervised loop. Orchestrated by the Trainer class.

Online Live Evolution

During normal agent operation, an EvolutionRail captures trajectories from each invoke, detects signals in real-time, and triggers skill/prompt evolution asynchronously in the background.

RL Reinforcement Learning

Collect multi-turn rollouts from agent interactions, compute rewards, and train the underlying LLM using PPO/GRPO via the Verl framework. Supports both offline (batch rollout) and online (gateway-based) modes.

4. Dataset (Case / EvaluatedCase)

agent_evolving/dataset/case.py

Case

A single training/evaluation sample:

  • inputs: Dict — the query or conversation to send to the agent
  • label: Dict — the expected answer or desired output
  • tools: Optional[List[ToolInfo]] — tools available for this case
  • case_id: str — auto-generated unique identifier

EvaluatedCase

Wraps a Case with the agent's prediction and evaluation result:

  • case: Case — the original case
  • answer: Dict — the agent's output
  • score: float — composite score in [0, 1]
  • reason: str — why this score was given
  • per_metric: Optional[Dict[str, float]] — per-metric breakdown

CaseLoader loads cases from files (JSON, etc.) and provides get_cases().

agent_evolving/evaluator/evaluator.py

Class Description
BaseEvaluator Abstract base with evaluate(case, predict) and batch_evaluate() (parallel via ThreadPoolExecutor)
DefaultEvaluator Uses LLM-as-judge: sends question + expected answer + model answer to an LLM, parses pass/fail result (score 0 or 1). Includes retry on parse failure.
MetricEvaluator Aggregates one or more Metric plugins with configurable aggregation (mean, first). Supports per-metric breakdown.

6. Trajectory

agent_evolving/trajectory/types.py

A Trajectory is the complete execution trace of an agent invocation — every LLM call and tool call, with full input/output data.

Trajectory
├── execution_id: str           # Unique ID for this run
├── source: "offline"|"online"  # Where it was captured
├── case_id: Optional[str]      # Dataset case (offline)
├── session_id: Optional[str]   # Conversation session (online)
├── cost: CostInfo              # Token usage aggregation
├── meta: Dict                  # Extension metadata
└── steps: List[TrajectoryStep]
    │
    ├── TrajectoryStep (kind="llm")
    │   ├── detail: LLMCallDetail
    │   │   ├── model: str
    │   │   ├── messages: List[Dict]    # Full message history
    │   │   ├── response: Dict          # LLM response
    │   │   ├── tools: List[Dict]       # Tool definitions sent
    │   │   └── usage: Dict             # Token counts
    │   ├── prompt_token_ids: List[int] # Lifted from response
    │   ├── completion_token_ids: List[int]
    │   ├── logprobs: Any               # Token-level log probabilities
    │   └── meta: Dict (operator_id, invoke relationships)
    │
    └── TrajectoryStep (kind="tool")
        ├── detail: ToolCallDetail
        │   ├── tool_name: str
        │   ├── call_args: Any
        │   ├── call_result: Any
        │   ├── tool_description: str
        │   └── tool_schema: Dict
        └── meta: Dict (operator_id, tool_call_id)

Extraction

TracerTrajectoryExtractor converts a Session object into a Trajectory by reading the session's tracer spans. Each span is classified as "llm", "tool", or "agent" and converted into the appropriate step type.

For team scenarios, TrajectoryAggregator merges trajectories from multiple members into a single cross-member trajectory with collaboration metadata.

7. Signal Detection

agent_evolving/signal/

Signals are the bridge between "something went wrong" and "here's what to optimize".

EvolutionSignal

  • signal_type: What happened — "execution_failure", "user_correction", "low_score", "script_artifact", "collaboration_*"
  • evolution_type: SKILL_EXPERIENCE or NEW_SKILL
  • section: Target SKILL.md section — "Troubleshooting", "Examples", "Scripts", "Collaboration"
  • excerpt: Relevant text snippet from the conversation
  • tool_name / skill_name: Context about which tool or skill was involved

Two Signal Sources

Offline: from_eval.py

Converts EvaluatedCase → EvolutionSignal. Low-score cases become "low_score" signals. Non-zero scores become "evaluated" signals. Includes question, label, answer, reason, and score as context.

Online + Offline: ConversationSignalDetector

Scans Trajectory or raw message lists for patterns:

  • Execution failures: regex matches for error/exception/traceback in tool output
  • User corrections: patterns like "不对", "should be", "actually"
  • Script artifacts: successful code execution captured as reusable scripts
  • Skill reads: tracks which SKILL.md files the agent accessed
  • Collaboration signals: send_message, claim_task, view_task in team context

8. Optimizers

agent_evolving/optimizer/

Optimizers are dimension-specific strategies that consume signals and trajectories, then produce parameter updates. They follow a backward → step pattern inspired by neural network training:

Signals + Trajectories
→
backward()
analyze failures, generate gradients
→
step()
produce Updates dict
→
Updates

BaseOptimizer

Common skeleton for all optimizers:

  • bind(operators, targets) — filters operators that expose the target tunables
  • add_trajectory() — caches trajectories for analysis
  • backward(signals) — analyzes failure signals, generates textual gradients
  • step() — produces the Updates dict to apply

Each optimizer has a domain (e.g., "llm", "tool", "skill") and TextualParameter containers holding the generated gradients.

Dimension-Specific Optimizers

Optimizer Domain What it optimizes How
InstructionOptimizer llm System prompt, user prompt Uses LLM to generate textual gradients (explanations of why the prompt failed), then rewrites the prompt. All LLM calls happen in backward(); step() returns pre-computed results.
ToolOptimizerBase tool Tool descriptions Two-stage pipeline: (1) generate example interactions, (2) rewrite descriptions. Uses beam search and custom reviewers. Black-box: requires_forward_data() = False.
SkillExperienceOptimizer skill SKILL.md content (description, body, scripts) Consumes EvolutionSignals from conversations, uses LLM to generate EvolutionRecords (patches to skill sections). Scores records by signal type. Supports online and offline modes.
MemoryCallOptimizer memory Memory retrieval parameters Optimizes memory operator tunables.

9. Updater (Single-Dim & Multi-Dim)

agent_evolving/updater/

The Updater protocol is the convergence point between the Trainer and the Optimizers. The Trainer doesn't know about specific optimizer implementations — it only calls updater.update(trajectories, evaluated_cases).

SingleDimUpdater

Wraps a single BaseOptimizer. Flow:

  1. Feed trajectories to the optimizer
  2. Convert EvaluatedCases to EvolutionSignals
  3. Call optimizer.backward(signals)
  4. Call optimizer.step() → returns Updates

MultiDimUpdater

Manages multiple domain optimizers (e.g., LLM + Tool + Memory). Performs attribution/allocation — distributes bad-case signals to the responsible operator domain — then runs each domain's optimizer independently and merges the resulting Updates.

The Updates type is Dict[Tuple[operator_id, target], value] — a flat dictionary mapping each (operator, parameter) pair to its new value.

10. Trainer (Orchestrator)

agent_evolving/trainer/trainer.py

Trainer is the top-level orchestrator that ties everything together:

trainer = Trainer(
    updater=SingleDimUpdater(InstructionOptimizer(model_config, client_config)),
    evaluator=MetricEvaluator([ExactMatchMetric()]),
    num_parallel=4,
    early_stop_score=0.95,
    checkpoint_dir="./checkpoints",
)

trained_agent = trainer.train(
    agent=my_agent,
    train_cases=CaseLoader.from_file("train.json"),
    val_cases=CaseLoader.from_file("val.json"),
    num_iterations=10,
)

Training Loop Detail

  1. Bind: updater.bind(agent.get_operators()) — discovers which operators have tunable parameters
  2. Baseline: Evaluate agent on validation set to get starting score
  3. Epoch loop (up to num_iterations):
    1. Forward: Run agent.invoke() on each training case (parallel), collect Sessions
    2. Evaluate: Score each prediction against labels
    3. Extract: Convert Sessions to Trajectories
    4. Update: updater.update(trajectories, evaluated_cases) → Updates or candidate list
    5. Apply: Write Updates back to operators via operator.set_parameter(target, value)
    6. Validate: Re-evaluate on validation set
    7. Checkpoint: Save if improved
    8. Early stop: Break if score ≥ threshold

Candidate Selection

If the updater returns List[Updates] (multiple candidates), the Trainer evaluates each on the validation set, selects the best, and commits it. Uses operator get_state()/load_state() for snapshot-rollback to avoid copying the Agent.

12. RL Training (agent_rl)

agent_evolving/agent_rl/

The RL subsystem extends the evolution framework with reinforcement learning, enabling the underlying LLM itself to be fine-tuned based on agent interaction outcomes.

Core Data Model

                    │         RLTask               │

                                  ▼

                    │     RolloutMessage           │
                    │  ┌─────────────────────────┐ │
                    │  │ Rollout (per LLM turn)   │ │
                    │  │  input_prompt (messages) │ │
                    │  │  output_response         │ │

                    │  │  output_response_ids     │ │

                    └─────────────┬───────────────┘
                                  │ Tokenized + rewarded

                    ┌─────────────────────────────┐
                    │     RolloutWithReward        │
                    │  input_prompt_ids            │
                    │  output_response_ids         │

                    └─────────────────────────────┘
                                  │
                                  ▼
                    ┌─────────────────────────────┐
                    │     PPO / GRPO Training      │
                    │  (via Verl framework)        │
                    └─────────────────────────────┘

Two RL Modes

Offline RL

OfflineRLOptimizer + RLRail

  • RLRail (extends EvolutionRail) captures trajectories with RL-specific metadata (turn_id, case_id)
  • ParallelRuntimeExecutor runs multiple agent instances concurrently to collect rollouts
  • TrainingCoordinator manages batch building, encoding, and PPO training
  • Uses Ray for distributed execution, Verl for PPO/GRPO training

Online RL

OnlineRLOptimizer + RLOnlineRail

  • RLOnlineRail captures trajectories during live agent operation and uploads to a gateway
  • Gateway (HTTP server) receives trajectories, dispatches to judge for reward scoring
  • JudgeServer evaluates trajectories and assigns rewards
  • OnlineTrainingScheduler triggers PPO training when enough rollouts accumulate
  • Supports LoRA weight updates and hot-swapping

Reward System

RewardRegistry is a global registry mapping reward function names to callables. Users register custom reward functions via @register_reward("name") decorator. The RL pipeline looks up the reward function by name at training time.

RL Configuration

RLConfig (Pydantic) covers:

  • TrainingConfig: model path, algorithm (GRPO/PPO), batch sizes, GPU config, sequence lengths
  • RolloutConfig: learning rate, KL loss, clip ratios, rollout count
  • AgentRuntimeConfig: system prompt, temperature, max tokens
  • PersistenceConfig: rollout saving, flush intervals
  • AdaConfig: optional adaptive rollout variant

13. Online Evolution (EvolutionRail)

harness/rails/evolution/evolution_rail.py

Beyond the offline batch pipeline, the framework supports live evolution during agent operation via the EvolutionRail (a DeepAgentRail that mounts on the agent).

How It Works

Agent runs normally
(invoke, model_call, tool_call)
→
EvolutionRail
captures trajectory
automatically
→
Trigger point fires
(after_invoke, after_task_iteration, etc.)
→
run_evolution()
detect signals
generate patches
→
Store evolution records
(EvolutionLog)

Key features:

  • Automatic trajectory collection: The base class handles all lifecycle hooks and builds Trajectory objects
  • Configurable trigger: Evolution can fire after invoke, after each model call, after each tool call, or after each task iteration
  • Async evolution: By default, run_evolution() runs in a background task to avoid blocking the agent
  • Subclass extension points: _on_before_invoke, _on_after_model_call, _on_after_tool_call, _on_after_invoke, run_evolution

Two concrete subclasses are used in production:

  • SkillEvolutionRail — runs SkillExperienceOptimizer on captured trajectories to evolve skill content
  • TrajectoryRail — stores trajectories for later batch analysis

14. Putting It All Together

Offline Evolution Example

# 1. Define evaluation cases
cases = CaseLoader.from_list([
    Case(inputs={"query": "Fix the login bug"}, label={"answer": "Bug fixed in auth.py"}),
    Case(inputs={"query": "Add unit tests"}, label={"answer": "3 tests added"}),
])

# 2. Create optimizer + evaluator
optimizer = InstructionOptimizer(model_config=..., model_client_config=...)
evaluator = MetricEvaluator([ExactMatchMetric(), LLMAsJudgeMetric(...)])

# 3. Create trainer
trainer = Trainer(
    updater=SingleDimUpdater(optimizer),
    evaluator=evaluator,
    num_parallel=4,
    checkpoint_dir="./evolve_checkpoints",
)

# 4. Run evolution
trained_agent = trainer.train(
    agent=my_agent,
    train_cases=cases,
    num_iterations=5,
)
# Agent's system prompt has been optimized based on failure analysis

Online Evolution Flow

# EvolutionRail is mounted on the agent during construction
# (via DeepAgentConfig or TeamAgentSpec)

# During normal operation:
#   1. User sends a query
#   2. Agent processes it (LLM calls + tool calls)
#   3. EvolutionRail captures the full trajectory
#   4. After invoke completes, run_evolution() fires:
#      - ConversationSignalDetector scans for failures/corrections
#      - SkillExperienceOptimizer generates EvolutionRecords
#      - Records are stored in EvolutionLog
#      - Pending changes await user approval
#   5. Next invocation benefits from the evolved skill content

RL Training Flow

# 1. Configure RL
config = RLConfig(
    training=TrainingConfig(
        model_path="/path/to/base_model",
        algorithm_adv_estimator="grpo",
        train_batch_size=32,
    ),
)

# 2. Create optimizer
optimizer = OfflineRLOptimizer(config)
optimizer.set_task_data_fn(my_task_generator)
optimizer.set_reward_fn("my_reward")

# 3. Run training (collects rollouts via ParallelRuntimeExecutor, trains via Verl PPO)
optimizer.train()

Key Design Principles

  • Operator abstraction: All evolvable parameters are exposed via Operator.get_tunables(). Optimizers never touch the agent directly.
  • Updater as convergence point: Trainer only knows about Updater.update(). Single-dim and multi-dim are interchangeable.
  • Signal-driven: Optimization is triggered by detected signals (failures, corrections, low scores), not blindly applied.
  • Candidate selection: When multiple update candidates exist, the best is selected via validation — no risky untested changes.
  • Checkpoint & resume: Full state persistence enables long-running evolution jobs to be interrupted and resumed.
  • Rail-based online evolution: Zero overhead when not active; seamless integration with the existing Rail lifecycle system.
